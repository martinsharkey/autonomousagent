# Sandbox Runner Documentation

## Overview

The sandbox runner provides a secure, isolated environment for executing untrusted code generated by the autonomous agents. It uses Docker containers with strict security constraints to prevent host system access.

## Security Features

- **Non-root user**: Runs as unprivileged `sandbox` user
- **Read-only filesystem**: Container filesystem is read-only except for `/tmp`
- **No new privileges**: Prevents privilege escalation
- **Dropped capabilities**: All Linux capabilities dropped except minimal required ones
- **Network isolation**: Internal Docker network with no external access by default
- **Temporary workspace**: Code executes in `/tmp/sandbox_workspace` with restricted permissions

## Building the Sandbox

```powershell
docker-compose -f docker-compose.sandbox.yml build
```

## Running the Sandbox

### Interactive Mode
```powershell
docker-compose -f docker-compose.sandbox.yml run --rm sandbox python
```

### Execute a Script
```powershell
docker-compose -f docker-compose.sandbox.yml run --rm sandbox python /tmp/sandbox_workspace/script.py
```

### Using the Python API
```python
from core.sandbox import execute_in_sandbox

result = execute_in_sandbox("print('Hello from sandbox')")
print(result)
```

## Security Constraints

### What's Blocked
- Network access (internal network only)
- Writing to filesystem (except `/tmp`)
- Privilege escalation
- Access to host system
- Long-running processes (timeout enforced)

### What's Allowed
- Python code execution
- Reading copied files
- Writing to `/tmp/sandbox_workspace`
- Basic system calls for Python runtime

## Migration to Production Sandboxes

For production use, migrate to hardware-level isolation:

### Firecracker MicroVMs (E2B, Modal)
- Kernel-level isolation
- Sub-second startup
- Strong security guarantees

### gVisor/Kata Containers (Northflank)
- Application kernel
- System call filtering
- Container-compatible

### Migration Steps
1. Update `core/sandbox.py` to use MicroVM API instead of Docker
2. Configure network policies for controlled external access
3. Implement resource limits (CPU, memory, disk)
4. Add monitoring and logging integration
5. Test with adversarial code samples

## Testing Isolation

Verify sandbox isolation:
```python
# Test 1: No host filesystem access
test_code = """
import os
try:
    os.listdir('/')
    print('FAIL: Can access host filesystem')
except:
    print('PASS: Filesystem isolated')
"""

# Test 2: No network access
test_code = """
import socket
try:
    socket.create_connection(('8.8.8.8', 53))
    print('FAIL: Can access network')
except:
    print('PASS: Network isolated')
"""

# Test 3: No privilege escalation
test_code = """
import os
if os.getuid() == 0:
    print('FAIL: Running as root')
else:
    print('PASS: Running as non-root')
"""
```

## Troubleshooting

### Container Won't Start
```powershell
docker-compose -f docker-compose.sandbox.yml logs
```

### Permission Denied
```powershell
docker-compose -f docker-compose.sandbox.yml run --rm sandbox ls -la /tmp/sandbox_workspace
```

### Network Access Needed (Development Only)
Edit `docker-compose.sandbox.yml` and remove `internal: true` from network config.

## Resource Limits

Add to `docker-compose.sandbox.yml`:
```yaml
services:
  sandbox:
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 512M
        reservations:
          cpus: '0.5'
          memory: 256M
```
